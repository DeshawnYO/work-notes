# 发布管理

## 安装包位置

统一使用 `releases/windows/<产品版本>/`。每个版本含原始 `.exe`（仅本地）、README.md、release.json、SHA256.txt、LICENSE、NOTICE.md；GitHub 中实际安装包上传到对应 Release 附件。总入口为 [安装包目录](../releases/README.md)。

GitHub 普通 Git 文件上限为 100 MiB，本项目安装包约 222 MiB，因此不能作为普通源码文件提交。GitHub Release 单附件上限为 2 GiB，适合分发这些安装包。官方规则见 [大文件管理](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github) 和 [Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。不拆分安装包、不向 Git 历史写入大型二进制。

## 新版本发布

1. 更新 app_version.py、CHANGELOG 与版本说明，确认数据兼容、许可及已知限制。
2. 从已记录的源码提交创建干净构建，使用现有 packaging/windows 构建入口，不覆盖任何旧版本产物。
3. 检查最终文件清单排除个人数据，记录真实源码提交、依赖、数据结构、包大小和 SHA-256。未知字段保留 null，不能补造。
4. 完成影响范围对应的验证；实际安装、升级、托盘、卸载、离线环境须单独记录。未验收的版本用试用 / 预发布状态。
5. 创建版本目录，提交说明、release.json、SHA256.txt 和许可。将 .exe 及许可/校验/发布信息附件上传至同一 GitHub Release，再公开 Release。
6. 对照 GitHub 附件大小和服务器 SHA-256 与本地原包；校验下载入口，保持版本目录与 Release 一致。

历史包使用 installer-v<版本> 归档标签，仅指向索引提交，不代表原始构建源码。新版本使用正常产品标签并记录实际构建提交。首次公开源码标签 v2.1.0-source.1 保持不变。

## 不覆盖与更正

已公开安装包、标签、校验值不覆盖或移动。安装包有修改时增加版本号；仅说明更正可提交新文档，但注明原因并保留历史包校验值。

本次历史包归档未重新构建，也未进行安装、升级或新电脑离线验收。旧只读解包工具不支持当前 Inno Setup 格式；文件审查依据原始构建清单与保留构建目录逐项校验，不能视为安装包直接解包验收。

## 升级和回退

关闭旧程序后安装。升级前备份数据库和所有外部项目文件、个人 Word；运行中的 SQLite 使用一致性备份。降级前判断数据结构兼容，不兼容时恢复升级前快照并另存新记录。不会自动替换作者日常程序。
