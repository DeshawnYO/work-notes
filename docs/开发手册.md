# 工作笔记开发手册

面向接手本项目的 agent 和开发者。更新日期：2026-10-12。本文描述整理后的真实源码结构；未来规划均单独标明。

## 1. 接手顺序与边界

1. 阅读根目录 `AGENTS.md` 和本手册。
2. 阅读用户本轮需求，再按任务阅读 `docs/requirements/V2.0.md`、`docs/DESIGN.md` 或版本规划。
3. 确认正在修改源码根目录，检查本轮已有改动；有 Git 时先查看工作区状态，没有 Git 时不能虚构提交或标签。
4. 用独立开发数据和项目目录运行，完成最小必要验证；汇报真实结果和剩余限制。

用户要求：**不要引用任何技能，除非用户主动告诉你要用什么技能。**

项目是 Windows 单用户、本机保存的个人工作管理工具，现名“工作笔记”。当前最新预发布构建为 2.2.0-beta.2（自选时间报告、集中模板和档案生成迭代），沿用 V2.1 编辑风；2.0.0-beta.2 与 1.0.0 历史包保留，日常安装版未替换。前端是原生 HTML/CSS/JavaScript，服务端是 Python 标准库 HTTP 服务与 SQLite；Windows 窗口是 C# WinForms + WebView2。没有 Node 前端构建链，也没有现成的云端后端或跨端同步服务。

原始需求对话与本机迭代验收记录仅保留在作者本地，不随公开源码分发。公开需求方向见 `requirements/V2.0.md`，当前实现与已知限制见根目录 `README.md`、`CHANGELOG.md` 和后续 Issue。子事项完成后仍由用户手动完成父事项，这是当前实现默认值，并非已确认业务规则。

## 3. 运行环境与独立开发启动

### 3.1 环境

原工程使用本机 `C:\Python314\python.exe`。当前便携运行时构建明确要求 **Windows x64 Python 3.14**；普通源码开发需确认所选解释器及依赖可用。`requirements.txt` 是部分依赖声明，没有锁定全部版本。便携构建还读取 `build_portable.py` 的 `DEPENDENCIES` 并复制相应包，不能只安装 requirements 后就承诺可以打包。

浏览器 UI 可直接访问本地服务。Node 仅可用于 JavaScript 语法检查，不是应用运行依赖。`vendor/pypdf` 是当前离线 PDF 提取依赖，不能当作垃圾缓存删除。

### 3.2 开发启动命令

在专用 PowerShell 终端中执行；确认解释器存在且可运行。端口示例为 18765，如果已被占用换一个空闲端口，不关闭别人的进程。

```powershell
Set-Location -LiteralPath 'D:\01-yangxiao\001-产品经理工作台'
$devPython = 'C:\Python314\python.exe'
& $devPython --version
$devRunName = (Get-Date -Format 'yyyyMMdd-HHmmss') + '-' + [guid]::NewGuid().ToString('N').Substring(0, 6)
$devRunDir = Join-Path (Get-Location) ('.local\dev-runs\' + $devRunName)
New-Item -ItemType Directory -Path (Join-Path $devRunDir 'data') -Force | Out-Null
New-Item -ItemType Directory -Path (Join-Path $devRunDir 'projects') -Force | Out-Null
$env:PERSONAL_WORKBENCH_DATA_DIR = Join-Path $devRunDir 'data'
$env:PERSONAL_WORKBENCH_PORT = '18765'
$env:PERSONAL_WORKBENCH_DISABLE_SCHEDULER = '1'
& $devPython -B -X utf8 server.py
```

另开浏览器访问 `http://127.0.0.1:18765/`。请求 `/api/health`，核对 `installation` 指向源码根目录、`data_dir` 指向本次 `.local/dev-runs/`。结束后 Ctrl+C 关闭这个服务，关闭专用终端，避免开发环境变量影响其他启动。

创建示例项目时只能选择本次 `projects/` 下的子目录。不要接入日常真实项目，不配置真实云端连接或复制 API Key。关闭调度器只关闭自动任务，用户主动点击的整理或模型连接测试仍可能调用模型，因此验证时也需要模拟响应或完全不启用模型。

不要用 `启动工作台.vbs` 做隔离验证：`launcher.py` 可能优先沿用 `dist/个人工作台-便携版/data/` 的数据库，并会处理同目录旧后台。安装版则由窗口程序选择外部数据目录、使用独立配置目录和动态端口；默认 18763 不通不能证明安装版没运行。

## 6. 数据与兼容

- `PERSONAL_WORKBENCH_DATA_DIR` 决定数据目录；不设置时 `core.py` 使用根目录 `data/`。仅导入 core 也会创建该目录，因此临时验证必须在导入之前配置环境变量。
- SQLite 文件为 `workbench.sqlite3`，数据库使用 WAL。运行中备份使用 SQLite backup API，不把单独复制主数据库文件当作一致性备份。
- 数据库保留真实项目的外部路径。复制数据库不等于隔离项目文件；升级验证使用快照并替换项目路径为副本，附件与档案也按改动范围备份。
- 设置中的数据库备份不等于项目文件备份。卸载保留外部数据的行为也不等于可以随便删除源码里的 `data/`、`dist/` 或私人备份。
- 模型密钥经当前 Windows 用户 DPAPI 加密。迁移到另一账户/电脑可能需要重新配置；不要改成明文，也不要打印密钥或完整敏感请求。
- 项目删除保留原文件及历史事实；档案编辑保存前保留历史，过期版本冲突时保留用户输入。

V2 在原有建表/增列流程后，由 `v2_data.py` 运行带编号的有序迁移 2、3、4，记录在 schema_migrations；新增随手记录、子事项、重大汇报、归档历史、个人 Word 相对路径。迁移保留原事项和日志，不删除历史记录。新增子事项等结构时，应设计有顺序、可重复执行且能识别失败的迁移，并明确旧程序兼容性。回退程序前判断数据兼容；不兼容时恢复升级前快照，另行保留升级后的新增记录。

`data_storage.py` 提供 `inspect/create/migrate --target ... [--source ...]`。create 和 migrate 会写目标目录，inspect 入口也会检查目录可写性；不要在真实路径上把它当成完全无副作用的诊断命令。

## 7. 构建方式与现有限制

### Windows 安装版

构建入口为 `packaging/windows/build_installer.py`，读取根目录后端、`static/`、`vendor/` 和品牌文件，编译 `WorkNotes.cs`，然后用 Inno Setup 打包。

已保留 `build/tools/`、`build/downloads/`，因为现有构建依赖其中的 Inno Setup、WebView2 SDK/运行环境等文件。`fetch_tools.py` 是仍有用途的下载工具，但会联网并选择当时可用的 SDK 版本，运行前检查当前工具记录；后续建议固定依赖版本。

以下为 V2 构建入口。`app_version.py` 统一产品/程序集/数据结构版本；构建使用独立暂存目录和 `releases/windows/<版本>/` 输出，拒绝覆盖已有安装包。再次构建已完成版本前应先递增版本。

```powershell
& 'C:\Python314\python.exe' -B -X utf8 packaging/windows/build_installer.py --stage-only
& 'C:\Python314\python.exe' -B -X utf8 packaging/windows/build_installer.py
& 'C:\Python314\python.exe' -B -X utf8 packaging/windows/release_metadata.py
```

`--stage-only` 仍会复制源码、编译窗口、写程序清单，只是不生成安装包，不是只读预览。V2 每次创建带版本和时间的干净暂存目录，拒绝复用已有目录。

当前服务、启动器、安装脚本和发布说明读取 `app_version.py`。健康接口数字 `version: 2` 仍为 API 版本；产品版本以 product_version 为准。构建时生成程序集版本，不修改历史产物。

已发布安装包不包含私人数据库和项目文件。构建脚本会检查部分危险文件类型/目录，但仍需核查最终程序清单和实际安装包；不要只因脚本声称干净就完成验收。

### 便携版

入口为 `build_portable.py`，会复制本机运行时、当前数据库快照和所有已接入项目，因此属于私人搬家工具。它不是向其他用户发布干净程序的入口。指定新目标时可用 `--output`；脚本拒绝覆盖已有目标。不要删除 `prepare_move.py`、启动脚本或运行时，它们仍为旧便携使用流程服务。

### 鸿蒙

`scripts/prepare_harmonyos.py` 只同步前端和品牌资源；`packaging/harmonyos/README.md` 记录未完成项。现阶段没有可验收的 HAP，不能把同步资源描述为移植完成。

## 8. 验证要求

本次按用户要求移除了历史测试脚本，没有新增常驻测试套件。不得在手册或汇报中继续引用已删除的 `tests/test_*.py` 命令作为当前验证入口。确有需要时只在 `.local/` 创建针对本次改动的临时验证，完成后清理；不要自动恢复整套历史脚本。

| 改动类型 | 必要验证 |
|---|---|
| Python 逻辑/接口 | 语法检查，独立环境实际调用相关流程，检查失败及重开后的状态 |
| JS/CSS/布局 | JS 语法、样式重建、浏览器实际交互、错误日志、桌面与手机截图 |
| 数据结构 | 用旧数据副本升级，核对保留内容和项目路径，重复升级及失败处理 |
| 档案/模型 | 模拟模型返回，成功、失败、冲突、取消、本地限制和原文保护 |
| 桌面/安装 | 构建后实际安装包验证首次启动、数据选择、升级、保存、托盘、重开和卸载保留 |
| 文档/清理 | 重新读取最终文件、检查路径和依赖、比较保留程序及安装包的校验值 |

Python 可用标准库 `ast.parse` 检查源码，不必运行业务模块，也避免生成 pycache；JS 可用 `node --check static/app.js`。语法检查不等于业务或视觉验收。

界面变更至少覆盖桌面 1440×900、较窄桌面 1280×720，以及手机 390×844；空间相关改动再查 320×600。重点检查日期切换、昨日顺延、事项状态、目标关联、记录筛选、未保存保护、档案章节、报告编辑导出和导航遮挡。按本轮改动选必要流程，不重复无关测试。
